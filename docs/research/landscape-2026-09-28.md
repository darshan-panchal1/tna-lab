# Self-hosted LLM eval tools fragment, then converge

The 2025–2026 self-hostable LLM evaluation and observability market has split cleanly into two camps, and only one of them is real competition for a genuinely open entrant: a small cluster of Apache-2.0/MIT/ELv2 tools — **Arize Phoenix, Langfuse, Helicone, Comet Opik, TensorZero, TruLens, and OpenLLMetry** — that let anyone self-host the full product for free, versus a much larger cohort of well-funded "open source" brands — **Braintrust, W&B Weave, LangSmith, Confident AI, Galileo, and PromptLayer** — whose self-hosting is gated entirely behind Enterprise-tier sales contracts and license keys ([Braintrust comparison page](https://www.braintrust.dev/articles/best-self-hosted-ai-evals-tools-2026); [W&B Weave Self-Managed docs](https://docs.wandb.ai/weave/guides/platform/weave-self-managed); [Confident AI Self-Hosting docs](https://www.confident-ai.com/docs/self-hosting)). Underneath the product layer, the ingestion standard the whole category depends on — OpenTelemetry's GenAI semantic conventions — is still explicitly in "Development" (pre-stable) status with no tagged release, and it coexists uneasily with Arize's competing OpenInference vocabulary, whose relationship to the official spec remains an open, unanswered question on GitHub ([John Hodge, July 2026 status write-up](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/); [Arize-ai/openinference issue #2130](https://github.com/Arize-ai/openinference/issues/2130)). Every platform that has earned a reputation for being useful — Langfuse, LangSmith, Confident AI — earns it through **dataset versioning and run comparison**, not through scoring-math innovation, since all of them delegate judge execution to either their own thin model classes or an external library. And every platform that tried to build a "pick your provider" abstraction for the judge model has documented, still-open breakage from it — DeepEval's judge catalog crashes on unrecognized OpenAI-compatible model IDs, and Langfuse's LLM Connections feature has an unresolved GitHub discussion where a LiteLLM-proxied endpoint fails at the abstraction's own validation step, not at the model call itself ([DeepEval issue #3133](https://github.com/confident-ai/deepeval/issues/3133); [Langfuse discussion #8689](https://github.com/orgs/langfuse/discussions/8689)). Given that evidence, the defensible first slice for tna-lab is narrow and specific: a library+CLI that ingests records into a versioned local dataset, calls trust-no-agent as an opaque `records -> scores` function with JUDGE_MODEL/GENERATOR_MODEL passed straight through uninterpreted, persists the run as a file, and diffs two runs against the same dataset snapshot — nothing else.

## Free self-hosting is the exception, not the norm

Counting every platform researched, **only seven of thirteen** offer a self-hosting path with no license key, sales contact, or paywalled feature tier: Phoenix, Langfuse, Helicone, TruLens, OpenLLMetry, Comet Opik, and TensorZero. Phoenix installs via a single `pip install arize-phoenix; phoenix serve` or one Docker image, and Arize's own license page states plainly that "there are no feature gates — Phoenix is a fully open-source platform" under the Elastic License 2.0 ([Phoenix License docs](https://arize.com/docs/phoenix/self-hosting/license)). Comet Opik, Apache-2.0 licensed with roughly 20,700 GitHub stars, makes the same claim even more explicitly: self-hosting via Docker Compose or Helm gives "access to all Opik features including tracing, evaluation, etc but without user management features," meaning only SSO/team-admin functionality — not core eval capability — is the enterprise-gated piece ([Opik GitHub](https://github.com/comet-ml/opik)). TensorZero, also Apache-2.0 with 11.7k stars, is architecturally the most ambitious of the free tier, unifying an LLM gateway, observability, evaluation, and optimization into one self-hostable system that claims roughly 1% of global LLM API spend flows through it ([TensorZero GitHub](https://github.com/tensorzero/tensorzero)). Langfuse, the most-starred tool in the category at 32.4k stars, is MIT-licensed at its core but carves out an Enterprise Edition license for a defined, narrow set of directories — organization creators, the instance management API, and UI customization — leaving tracing, evals, and datasets on the free side ([langfuse/LICENSE](https://github.com/langfuse/langfuse/blob/main/LICENSE)). Against that backdrop, the paid-gated cohort is remarkably uniform in its messaging: Braintrust's own marketing content concedes that Langfuse and Phoenix offer "free open-source self-hosting with no licensing costs," implicitly admitting its own Enterprise-only self-hosting does not ([Braintrust comparison page](https://www.braintrust.dev/articles/best-self-hosted-ai-evals-tools-2026)); W&B Weave's self-managed deployment requires a "Weave-enabled license from W&B Support" plus a minimum 7-pod, 180Gi Kubernetes/ClickHouse/S3 footprint with no lightweight option at all ([W&B Weave Self-Managed docs](https://docs.wandb.ai/weave/guides/platform/weave-self-managed)); and LangSmith, Confident AI, Galileo, and PromptLayer each require a vendor-issued license key for anything beyond their hosted cloud product ([Self-hosted LangSmith docs](https://docs.langchain.com/langsmith/self-hosted); [Confident AI Self-Hosting docs](https://www.confident-ai.com/docs/self-hosting); [Galileo Deployments Overview](https://docs.galileo.ai/deployments/overview); [PromptLayer Self-Hosted docs](https://docs.promptlayer.com/self-hosted)). Within the free tier, the operational burden still varies sharply: TruLens and OpenLLMetry are pure libraries/SDKs with no server to deploy at all ([GitHub - truera/trulens](https://github.com/truera/trulens); [openllmetry README](https://github.com/traceloop/openllmetry/blob/main/README.md)), Phoenix is a single binary or container, Opik and Helicone ship "all-in-one" Docker images with documented rough edges (Helicone's bundled image has no email service, wipes data on restart without mounted volumes, and its port 8585 proxy requires the operator to add firewalling manually), and Langfuse requires the heaviest production stack — Postgres, ClickHouse, Redis/Valkey, and S3-compatible storage across separate web and worker containers — reflecting a system built to process "90B+ observations per month" at scale ([Helicone self-host Docker docs](https://docs.helicone.ai/getting-started/self-host/docker); [Langfuse Self-Hosting Overview](https://langfuse.com/self-hosting)). For tna-lab, which must run as a library with no server required at all, this places it architecturally closer to TruLens and Opik's "servers are optional, not load-bearing" posture than to Langfuse's multi-service model — a meaningful validation that the "library + CLI, no server" constraint is not a compromise but a documented, viable position in this market.

## Two ingestion standards, neither stable, no bridge between them

Every OTel-native platform in this landscape rides on the same underlying primitive — a standard OpenTelemetry span with a specific attribute set — but two incompatible vocabularies populate that span, and neither is finished. The official **OpenTelemetry GenAI semantic conventions** were recently relocated entirely out of the main `opentelemetry-specification` repo into a dedicated `semantic-conventions-genai` repo, and as of a July 2026 community status check, "no GenAI-specific span, event, metric, or attribute in the dedicated repository is marked Stable," with the repo not even carrying a versioned release yet ([John Hodge, July 2026](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/)). The spec still churns version to version — v1.40.0 added retrieval spans and cache-token attributes, v1.41.0 split `invoke_agent` into separate client and internal spans — even as real vendors adopt it in production: VS Code Copilot, OpenAI Codex, and Claude Code all now emit `gen_ai.*`-convention traces, per OpenTelemetry's own 2026 blog post ([OpenTelemetry blog, 2026](https://opentelemetry.io/blog/2026/genai-observability/)). Running in parallel is **OpenInference**, Arize's own convention layer, which "largely predates" the OTel GenAI work and defines an entirely independent attribute vocabulary — a required `openinference.span.kind` taxonomy (`LLM`, `EMBEDDING`, `CHAIN`, `RETRIEVER`, `TOOL`, `AGENT`, and others) and flattened-indexed message attributes like `llm.input_messages.0.message.role`, none of which alias the `gen_ai.*` namespace ([OpenInference semantic_conventions.md](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md)). A GitHub issue explicitly asking Arize to clarify OpenInference's relationship to the official OTel work — including whether OpenInference will eventually be deprecated in its favor — has sat open with no maintainer response, and commenters have proposed a compatibility matrix that does not yet exist ([issue #2130](https://github.com/Arize-ai/openinference/issues/2130)). Phoenix itself, Arize's own product, treats OpenInference as the native format and requires a conversion package (`@arizeai/openinference-genai`) to translate incoming `gen_ai.*` spans — and that converter doesn't even exist for Phoenix's Go SDK path, which silently loses span-kind and structured message data when only OTel-GenAI attributes are present ([Phoenix docs, "Translating Semantic Conventions"](https://arize.com/docs/phoenix/tracing/concepts-tracing/translating-conventions)). Langfuse and LangSmith take the opposite posture, positioning themselves as convention-agnostic OTLP sinks: both accept raw OTLP at a dedicated endpoint and explicitly map both `gen_ai.*` and OpenInference-style attributes (LangSmith additionally documents mappings for Logfire and TraceLoop conventions) onto their own internal data model ([Langfuse OTel integration docs](https://langfuse.com/integrations/native/opentelemetry); [LangSmith "Trace with OpenTelemetry" docs](https://docs.langchain.com/langsmith/trace-with-opentelemetry)). The practical upshot for a new project is that there is no safe assumption of convergence: a new entrant should plan for two coexisting, independently-versioned conventions indefinitely, and if OTel ingestion is ever added to tna-lab, the cheapest, most future-proof posture is Langfuse's — accept raw OTLP and branch on whichever attribute is present (`openinference.span.kind` vs. `gen_ai.operation.name`) rather than committing to either vocabulary as canonical. Ready-made instrumentation exists for both paths already — OpenInference's per-framework `openinference-instrumentation-*` packages (LangChain, LiteLLM, CrewAI, Claude Agent SDK) and the official `opentelemetry-instrumentation-genai-*` family — so a new tool would not need to write its own instrumentation SDK regardless of which convention it favors ([PyPI: openinference-instrumentation-langchain](https://pypi.org/project/openinference-instrumentation-langchain/); [open-telemetry/opentelemetry-python-genai](https://github.com/open-telemetry/opentelemetry-python-genai/tree/main/instrumentation/opentelemetry-instrumentation-genai-openai)).

## Datasets decouple from traces; comparison is a code-first primitive everywhere

Across Phoenix, Langfuse, and LangSmith, a dataset example is consistently treated as a **materialized, independent copy** of input/output/metadata — not a live view of the trace it came from — with an optional pointer (Langfuse's `sourceTraceId`/`sourceObservationId`, LangSmith's promote-from-trace workflow) preserving lineage without sacrificing reproducibility if the source trace is later deleted or mutated ([Langfuse Experiments Data Model](https://langfuse.com/docs/evaluation/experiments/data-model); [LangSmith Evaluation docs](https://docs.langchain.com/langsmith/evaluation)). Braintrust is the sole outlier, supporting a genuine live-reference mode where a dataset record's `input` field can point at a logged trace instead of copying it ([Braintrust Datasets docs](https://www.braintrust.dev/docs/platform/datasets)). Versioning across the category has converged on the same shape — an **append-only, timestamp-keyed history**, not a git-like DAG with diffs or branches. LangSmith's model is the most fully realized: every add/update/delete creates a new timestamped version, a human-readable tag (like `"prod"`) can be pinned to a specific timestamp, and an experiment can be re-run against an exact historical state via `as_of=<version>` ([LangSmith dataset versioning docs](https://docs.smith.langchain.com/evaluation/how_to_guides/version_datasets)). Langfuse mirrors this closely, including a dedicated "Run Experiments on Versioned Datasets" feature shipped in February 2026 specifically to let teams compare performance across dataset iterations or reproduce exact past results ([Langfuse changelog](https://langfuse.com/changelog/2026-02-11-versioned-dataset-experiments)). No tool surveyed — including Braintrust — documents a diff view *between two dataset versions themselves*; only "fetch the dataset as of version X" is supported, which is a real, category-wide gap rather than a research miss. Comparison of two completed **experiments**, by contrast, is universally code-first: Phoenix's `run_experiment()`, Langfuse's `run_experiment()`, and LangSmith's `evaluate()` all execute entirely through the SDK with no UI required, returning structured objects carrying per-example and aggregate scores ([Phoenix run-experiments tutorial](https://arize.com/docs/phoenix/datasets-and-experiments/tutorial/run-experiments-with-code-evals); [Langfuse Experiments via SDK docs](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk)). LangSmith has the cleanest first-class comparison primitive: `evaluate()` accepts two existing experiments as a `target` along with pairwise evaluator functions and returns a structured, per-run-ID score mapping "purely via code — no UI interaction is required to run the comparison" ([LangSmith pairwise evaluation docs](https://docs.langchain.com/langsmith/evaluate-pairwise)). Phoenix's equivalent — a "baseline" concept that flags cases where a score flipped correct→incorrect between two runs — is described only as UI behavior in the release notes, with no confirmed SDK-level diff object ([Phoenix release notes, baseline comparisons](https://arize.com/docs/phoenix/release-notes/07.2025/07.09.2025-baseline-for-experiment-comparisons)). This is the single clearest piece of prior art for tna-lab's second required capability: a `compare(run_a, run_b)` primitive that returns per-row score deltas and flags regressions/improvements is exactly what LangSmith already proves is both valuable and fully achievable without any server, and it is the one feature none of the free-tier self-hostable tools (Phoenix, Opik, TensorZero) document as a first-class code-level API — making it a genuine differentiation opportunity rather than a reimplementation of an existing solved problem.

## The provider-abstraction trap is real, documented, and worth avoiding entirely

Every platform researched builds *some* multi-provider judge abstraction rather than deferring purely to the caller's own client — Phoenix ships model classes per vendor (`OpenAIModel`, `AnthropicModel`, a `LiteLLMModel` catch-all), TruLens ships subclassable `Provider` classes, Langfuse centralizes "LLM Connections" as server-side, UI-configured state, and DeepEval mixes a CLI-set global default with per-metric Python overrides ([Phoenix evaluation-models.md](https://github.com/Arize-ai/phoenix/blob/docs/docs/api/evaluation-models.md); [Langfuse LLM Connections](https://langfuse.com/docs/administration/llm-connection); [DeepEval: Using Custom LLMs](https://deepeval.com/guides/guides-using-custom-llms)) — and the deeper and more centrally-validated that abstraction gets, the more concretely it breaks on exactly the shape of endpoint tna-lab depends on: a single, non-catalog, OpenAI-compatible endpoint. DeepEval's `OpenAIModel` performs a lookup against a hand-maintained `OPENAI_MODELS_DATA` catalog and **crashes outright** when a model ID isn't recognized, because it tries to read attributes off a `None` lookup result — a documented, still-open failure mode for anyone pointing DeepEval at an unlisted OpenAI-compatible model, which is structurally the same situation as pointing a judge at an NVIDIA NIM endpoint ([DeepEval issue #3133](https://github.com/confident-ai/deepeval/issues/3133)). The documented workaround, `LocalModel`, has its own sharp edges: its `base_url` must be the bare `/v1` root because the OpenAI SDK auto-appends `/chat/completions`, and it defaults `supports_multimodal()` to `True`, risking image payloads being sent to endpoints that cannot accept them. Langfuse's server-side abstraction shows the identical failure pattern from a different angle: a user attempting to point an LLM-as-Judge evaluator at an on-prem model behind a LiteLLM proxy — again, an OpenAI-compatible surface — hit a persistent, unresolved "connection error" at the LLM Connection's own save/validation step, despite confirmed network reachability ([Langfuse discussion #8689](https://github.com/orgs/langfuse/discussions/8689)). Even LiteLLM itself, the library several of these tools lean on specifically to *be* the universal provider abstraction, carries over 1,000 open GitHub issues, including provider-response-transform bugs where internal parameters leak into request bodies across providers ([DEV Community analysis](https://dev.to/pranay_batta/litellm-has-1000-open-github-issues-heres-what-three-of-them-reveal-3jeo); [LiteLLM issue #30301](https://github.com/BerriAI/litellm/issues/30301)) — and Ragas, which deliberately declines to build its own abstraction and instead wraps LangChain's `LangchainLLMWrapper`, still surfaces local-model JSON-parsing failures and "LLM is None" initialization errors that trace back to the layer it deferred to ([Ragas issue #1100](https://github.com/explodinggradients/ragas/issues/1100)). The generalizable lesson is that *deferring* to someone else's provider abstraction does not eliminate this class of bug, it only relocates it — which argues for a stance stronger than even Phoenix's `base_url` parameter or TruLens's subclassable `Provider`: no interception of the judge/generator configuration at all. This is precisely tna-lab's existing design (JUDGE_MODEL/GENERATOR_MODEL env vars routed straight through to trust-no-agent's own NIM-facing client, uninterpreted by tna-lab itself), and Part 1's evidence should be read as direct, independent confirmation that this is the correct architectural choice rather than an under-ambitious one — DeepEval, Langfuse, and LiteLLM are all mature, well-resourced projects, and all three still have open, unresolved bugs in exactly this layer.

## The minimal defensible slice: dataset, run, compare — nothing else

The research converges on a specific answer to "what is the smallest slice that's already more useful than calling trust-no-agent by hand": not scoring, but **persistence and comparison** of scoring runs. A bare call to trust-no-agent already produces scores; what evaporates at the end of a script, absent a platform, is any record of *which* config produced *which* scores against *which* dataset state — precisely the redundant bookkeeping work every user would otherwise rebuild themselves, and precisely what Langfuse, LangSmith, and Confident AI all center their value proposition on rather than on scoring math ([Langfuse Evaluation Overview](https://langfuse.com/docs/evaluation/overview); [LangSmith Evaluation docs](https://docs.langchain.com/langsmith/evaluation)). Every documented pain point uncovered in this research — DeepEval's model catalog, Langfuse's connection validation, LiteLLM's leakage bugs — lives in the judge-provider plumbing layer; none lives in the dataset/run-comparison layer, which is both comparatively cheap to build well and is where the evidence says the category's real, durable value sits. Concretely, that argues for a v1 built around three primitives, each with direct prior art: **(1) ingest and curate** — normalize raw records into a local, content-addressed dataset (JSONL plus a manifest hash, so re-ingestion is idempotent) and freeze named, immutable snapshots (`dataset freeze my-dataset@v1`), mirroring the append-only, timestamp-keyed versioning that LangSmith and Langfuse both converged on independently rather than inventing a git-like branch/diff model neither of them built either; **(2) run** — iterate a frozen dataset snapshot, call trust-no-agent's own scoring API exactly as its own docs specify with JUDGE_MODEL/GENERATOR_MODEL passed through unmodified, and persist a run record (per-row scores, trust-no-agent's own version/params, a run ID keyed to the dataset snapshot hash) as a plain local file — the same code-first pattern every serious platform in this research already proved works with no server; and **(3) compare** — a `compare(run_a, run_b)` call that returns a structured, per-row score-delta diff flagging regressions and improvements against a shared dataset snapshot, closing the one gap where even the free-tier self-hostable leaders (Phoenix, Opik) offer only a UI-level comparison rather than a documented SDK-level diff object, and where LangSmith's pairwise `evaluate()` is the clearest existing proof that this is buildable as pure code. Everything else surfaced in this research should be deliberately deferred, not because it is unimportant but because each item is either explicitly excluded by the project's own constraints or is the direct, cited source of a real bug in an existing mature tool: a provider abstraction (DeepEval, Langfuse, LiteLLM all show open breakage here); server-side/UI-stored configuration (Langfuse's friction surfaced specifically at that layer); a plugin system (DeepEval's provider table is effectively an informal, poorly-maintained one already); multi-tenant auth (no evidence anywhere in this research ties friction to authentication, so there is no urgency case for building it first); and re-implemented metrics (the category's mature, focused scoring libraries — including trust-no-agent itself — already own that surface well).

## Conclusion

The strongest signal out of this research is not which platform to copy but which layer of the stack is actually contested. Trace ingestion is unsettled at the standards level (two non-converging vocabularies, neither stable) and dataset/experiment mechanics have already converged on a shared, boring, timestamp-versioned pattern that any new entrant can adopt with low risk — but the judge-configuration layer is where mature, funded projects are still visibly bleeding, which means it is simultaneously the most tempting place to add "just one" convenience feature and the most dangerous place to do it. tna-lab's existing constraints — no provider abstraction, no server requirement, trust-no-agent as the sole scoring dependency — aren't just compatible with what this research found; they're a closer fit to the category's evidence than what most of the well-resourced incumbents actually shipped. The open strategic question this report cannot resolve is timing: nothing in the sources indicates how quickly users of file-based, local-first eval tools outgrow that model and start wanting a shared or hosted view, since every platform surveyed that started library-first (TruLens, and arguably early Phoenix) eventually grew a server component. That transition point, not the initial feature slice, is where tna-lab's next real design decision will land — and it should be made later, deliberately, and only once the dataset/run/compare core has proven itself, rather than pulled forward into v1 under the same instinct that produced DeepEval's provider catalog.
